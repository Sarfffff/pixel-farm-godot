## 游戏开发全流程（从创意到上线）

适用对象：本项目（Godot 4.7 / 2D 农场经营）。全流程按"软件工程 + 游戏制作"双视角组织：软件工程保证**可维护、可交付**，游戏制作保证**好玩、可验证**。

本文档回答三个问题：每个阶段**要做什么**、**做完交出什么**、**怎么判定真的做完了**。

---

### 0. 使用方法

1. 从阶段 0 顺序推进，不要跳阶段做内容——跳阶段是独立开发者最常见的返工来源。
2. 每个阶段末尾有"阶段门（Gate）"，**门不过不进下一阶段**，宁可砍范围也不要带着未验证的风险往下堆内容。
3. 每个阶段都维护三样东西：设计意图（为什么做）、产出物（做成了什么）、验收记录（怎么证明）。
4. 文档编号与阶段对应关系见 `docs/README.md`。

#### 阶段全景

| 阶段 | 名称 | 核心问题 | 典型产出物 | 建议时间盒（个人 + AI 辅助） |
| --- | --- | --- | --- | --- |
| 0 | 机会评估与立项 | 值不值得做？现有资源能支撑什么？ | 素材盘点、约束清单、风险登记表 | 1–2 天 |
| 1 | 概念设计与 GDD | 做成什么样才算好玩？ | 一页纸概念、GDD、范围表 | 2–4 天 |
| 2 | 技术原型（PoC） | 技术上行不行？ | 可丢弃的验证场景、结论记录 | 3–7 天 |
| 3 | 垂直切片 | 手感对不对？ | 10 分钟可玩闭环、美术基准 | 1–2 周 |
| 4 | 生产管线与技术架构 | 能不能持续、批量地产出？ | 项目结构、规范、数据表、CI/校验脚本 | 3–5 天 |
| 5 | 内容生产 | 内容够不够？ | 完整地图、美术、音频、数据配置 | 2–6 周（并行） |
| 6 | 系统开发与整合 | 各系统拼起来还成立吗？ | 全部玩法系统、UI、存档 | 4–8 周（并行） |
| 7 | 测试与 QA | 会不会崩、会不会卡死？ | 测试用例、bug 库、回归记录 | 贯穿，末期 1–2 周集中 |
| 8 | 平衡、打磨与引导 | 玩家能不能自己玩懂、玩爽？ | 数值终版、教程、体验打磨 | 2–3 周 |
| 9 | 发布准备 | 能不能装、能不能卖？ | 导出包、商店页、发布检查表 | 1–2 周 |
| 10 | 上线后运营 | 有没有人玩、要不要改？ | 补丁、数据看板、复盘文档 | 持续 |

> 时间盒是**约束**不是承诺：超时就砍范围，不加时间。个人项目真正的敌人是"范围膨胀"。

### 阶段 0：机会评估与立项

**目标**：用最低成本判断这个方向是否值得投入，以及现有资源能把项目撑到什么规模。

#### 必做事项

1. **资源盘点**：逐个清点已有素材（图片、音频、字体、UI），记录尺寸、格式、可用性、缺口。
2. **能力边界分析**：由素材反推"最适合做 / 可以做 / 做不了"的游戏类型，写成结论而非感觉。
3. **约束确认**：人（几个人、每周多少小时）、钱（是否买素材/工具）、技术（引擎版本、平台）、时间（目标上线日）。
4. **市场与参考**：列 3–5 个直接参考作品，记录它们的核心循环、美术量级、售价、玩家评价中的高频抱怨（那就是你的差异化机会）。
5. **风险登记**：把风险写成"风险 → 影响 → 概率 → 缓解手段 → 触发信号"，按影响排序。
6. **范围三档**：写下 MVP（必做）、Should（有余力做）、Won't（明确不做）。Won't 清单是防止范围膨胀的关键。

#### 产出物

- 素材盘点表（文件、尺寸、可复用点、缺口）
- 约束清单与目标平台
- 风险登记表（至少 5 条，含"美术量不足""存档不兼容""单局节奏太平"这类游戏向风险）
- 三档范围清单（MoSCoW）
- 立项结论：做 / 不做 / 换方向，一句话理由

#### 阶段门（Gate 0）

- [ ] 能用一句话说清"做什么类型、给谁玩、凭什么比参考作品更适合我"
- [ ] 素材缺口有明确对策（自制 / 买 / 砍功能），不是"以后再说"
- [ ] Won't 清单已写，且你接受不做这些
- [ ] 时间预算不超过可支配时间的 70%（留 30% 缓冲）

#### 常见坑

- 把"我很喜欢这个类型"当成可行性论证。
- 素材只有角色没有关卡/UI/音效，却按"完整游戏"估算工期。
- 一次性规划 3 年内容量，然后在第 3 周崩掉。

### 阶段 1：概念设计与 GDD

**目标**：把模糊的创意变成可执行、可验收的设计文档。

#### 必做事项

1. **一页纸概念（One-Pager）**：一句话定位、目标玩家、核心循环（30 秒内说清）、独特卖点、参考作品、目标平台与售价。
2. **玩家幻想与体验目标**：玩家想成为谁、想获得什么情绪（放松 / 成长 / 收集 / 掌控），并明确哪些体验**不做**（例如不做战斗紧张感）。
3. **核心循环分层**：
   - 秒级（走、挥锄头、拾取）
   - 分钟级（种一块地、浇一轮水）
   - 天级（睡觉、结算、卖货）
   - 周级（解锁新作物、扩建田地、买动物）
   每一层都要写清"玩家投入什么 → 得到什么 → 为什么再来一轮"。
4. **系统清单**：每个系统列目的、输入、输出、依赖的其他系统。农场项目典型清单：移动与碰撞、工具与交互、地形改造（锄地/浇水）、作物生长、时间与日历、经济与商店、背包与物品、动物、存档、UI/HUD、音频、教程。
5. **数值草案**：作物生长天数、售价与成本比、单日可操作次数、金币曲线。**先有数再写代码**，避免后期靠感觉调。
6. **内容量级表**：几张地图、几种作物、几种动物、几个 NPC、总游玩时长目标。
7. **UI 流程图**：从进游戏到退出的所有界面切换（含暂停、背包、商店、结算、存档提示）。
8. **范围复核**：拿 GDD 回阶段 0 的范围表对照，凡是不在 MVP 里的系统一律标灰。

#### 产出物

- `docs/03-GDD-游戏设计文档.md`（含核心循环图、系统表、数值草案、内容量级）
- 一页纸概念（可直接用于商店页/招募/自述）
- 灰盒流程图（哪怕用纸画）

#### 阶段门（Gate 1）

- [ ] 核心循环能用 3 句话讲给非玩家听懂
- [ ] 每个系统都有"不做会怎样"的说明，且有明确的取舍
- [ ] 数值草案能支撑"第 1 天体验"和"第 7 天体验"两个节点
- [ ] MVP 的系统数量在手写范围内（个人项目：核心 ≤ 6 个系统）

#### 常见坑

- GDD 写成小说：没有数值、没有流程图、没有验收标准。
- 系统之间依赖成环（背包依赖存档，存档又依赖背包却没定数据归属）。
- 只在脑子里设计"种田很有趣"，没算过"浇水 30 格要按 30 次键"的手感代价。

### 阶段 2：技术原型（PoC，可丢弃）

**目标**：在投入美术与内容前，把**技术未知项**逐一验证掉。原型允许丑陋，唯一要求是"给出结论"。

#### 必做事项

1. **列出技术未知项**，每个未知项一个最小验证场景：
   - 16×16 像素在目标分辨率下是否清晰（过滤、缩放、亚像素抖动）
   - TileSet 地形自动过渡能否覆盖草地/耕地/水边的所有组合
   - 角色与树/房屋的 Y 轴遮挡排序是否正确
   - 交互目标选取（面前那一格）是否稳定
   - 作物生长状态机 + 存档读档是否一致
   - 大量作物/掉落物时的帧率
2. **建立最小工程基线**：像素过滤 Nearest、基准分辨率与拉伸模式、输入映射、`physics` 层命名、调试用日志开关。
3. **写结论记录**：每个原型一段话——验证了什么、结论如何、是否引入技术债、正式实现用什么方案。
4. **定性能预算**：目标帧率、最大同时活动物件数、单帧脚本耗时上限、贴图内存上限。

#### 产出物

- `prototypes/` 或独立分支下的验证场景（明确标注"可丢弃"）
- 技术结论清单（进 `docs/04-技术设计文档.md` 的素材）
- 基线配置（像素/分辨率/输入/物理层）

#### 阶段门（Gate 2）

- [ ] 每个未知项都有"能做 / 不能做 / 需要换方案"的明确结论
- [ ] 像素画面在目标分辨率下不糊、不抖
- [ ] 出现失败项时已调整设计，而不是留着侥幸
- [ ] 原型代码有明确去向（丢弃 / 提炼成正式模块），不留半成品死代码

#### 常见坑

- 原型写得越来越漂亮，最后不敢删——原型一旦开始"顺便做完整功能"，工期就失控。
- 只验证"能不能跑"，不验证"跑起来好不好调"。
- 忽略存档：农场游戏的核心是**长期进度**，存档方案必须在阶段 2 就定，不能留到后期。

---

### 阶段 3：垂直切片（Vertical Slice）

**目标**：用**正式质量**做出一小段完整体验（10–15 分钟），证明"这个游戏好玩且做得出来"。

#### 必做事项

1. **切一条完整闭环**：进游戏 → 走位 → 拿工具 → 锄地 → 播种 → 浇水 → 等待（可加速）→ 收获 → 卖钱 → 买新种子 → 存档 → 退出 → 读档继续。
2. **美术基准**：确定调色板、瓦片对齐规则、精灵锚点（脚底中心）、阴影/描边规则、UI 字号与九宫格边框。后续所有美术按此生产。
3. **手感调优**：移动加速度、碰撞体大小（小于视觉体积）、交互判定范围、动作前摇/后摇、反馈（音效、粒子、数字弹出）。手感在这一阶段定死，后期只微调。
4. **UI 骨架**：HUD（金币、时间、手持物）+ 背包 + 提示条，用占位图形也要把布局定下来。
5. **内部试玩**：找 2–3 人盲玩，只记录"卡在哪、误解了什么"，不解释、不引导，观察 10 分钟。
6. **切片复盘**：实际耗时 vs 估算，哪个系统超支，据此重排后续计划。

#### 产出物

- 可运行切片构建（含存档）
- 美术/ UI 规范（进 `docs/04`）
- 试玩记录与结论（保留 / 调整 / 砍掉哪些设计）
- 更新的排期与范围表

#### 阶段门（Gate 3）

- [ ] 陌生玩家在无口头提示下能自己完成一次"种→收→卖"
- [ ] 没有任何占位资源（美工、字体、音效都是最终风格或明确替代方案）
- [ ] 存档退出再进入，进度、作物阶段、金币完全一致
- [ ] 控制台无 `SCRIPT ERROR` / `ERROR`
- [ ] 切片耗时估算能外推：完整版 ≈ 切片 × 系数（通常 4–8 倍）

> 这是整个项目最重要的门。**切片不好玩，就不要往里面堆内容。**

#### 常见坑

- 切片做成"功能演示"而不是"体验闭环"（能种地但没经济，能走但没有目标）。
- 手感留到后期再调，结果所有关卡和数值都建立在错误手感上。
- 试玩时不断解释"这里以后会加"，掩盖真实理解障碍。

### 阶段 4：生产管线与技术架构

**目标**：把"能跑"变成"能持续、批量、低返工地生产"。

#### 必做事项

1. **目录与场景结构定稿**：`scenes/`（按功能分子目录）、`scripts/`（按领域分）、`assets/`（按类型分）、`data/`（配置 Resource）。命名规则写进规范。
2. **架构分层**：
   - 表现层（节点、动画、UI）
   - 逻辑层（系统脚本、状态机）
   - 数据层（自定义 `Resource` 配置：作物表、物品表、商店表）
   - 全局服务（Autoload：游戏状态、时间、存档、音频、事件总线）
   明确"谁能改谁"，禁止 UI 直接改存档数据。
3. **数据驱动落地**：作物、物品、商店、掉落表全部做成 `.tres`，加内容不改代码。
4. **事件与解耦**：跨系统通信用信号/事件总线（如 `day_changed`、`item_obtained`），不用 `get_node("../../..")` 硬引用。
5. **存档方案定死**：序列化字段、版本号、兼容策略（旧档缺字段的默认值）、存档时机、损坏档处理。**存档格式一旦发布就不能随意改。**
6. **调试基建**：调试面板（给钱、跳时间、催熟）、日志分级、可开关的作弊键、场景直启（单独运行某场景）。
7. **质量闸门自动化**：脚本语法检查（`godot --headless --check-only --script`）、资源命名检查、导出前构建脚本、版本号统一（`project.godot` + 导出预设）。
8. **版本管理**：分支策略（主线 + 功能分支）、提交粒度（一提交一件事）、`.gitignore` 覆盖 `.godot/` 与导出产物、大文件策略（LFS 视素材量而定）。
9. **任务看板**：把 GDD 系统拆成 0.5–2 天的任务卡，标注依赖与验收标准。

#### 产出物

- `docs/04-技术设计文档.md`（结构、数据模型、存档格式、性能预算、调试手段）
- 代码规范（已在 `.codebuddy/rules/`，需与之保持同步）
- 数据表（作物/物品/商店）初版
- 构建与校验脚本
- 任务看板（可按里程碑筛）

#### 阶段门（Gate 4）

- [ ] 新增一种作物只需加一个 `.tres` + 一张图，不改逻辑代码
- [ ] 新增一个 UI 界面不需要动存档与游戏状态代码
- [ ] 存档有版本号，且有"旧档能读"的测试用例
- [ ] 一次提交能通过自动校验（语法 + 命名 + 导出构建）
- [ ] 任意系统能被单独启动调试，不必从头玩到那里

#### 常见坑

- 过早抽象：为一个功能造三层框架，结果框架比功能还重。抽象应由**第二次重复**驱动。
- 全项目塞进一个 `GameManager`，最后谁都不敢动。
- 配置散落在代码常量里，加内容就是改代码 + 重新测全流程。

---

### 阶段 5：内容生产

**目标**：批量产出玩法所需的地图、美术、音频与数据，且质量一致、可复用。

#### 必做事项

1. **生产清单化**：把 GDD 的内容量级表拆成条目（每张地图、每种作物 5 个阶段、每个 UI 图标、每条音效），逐条勾选，避免"感觉还差很多"。
2. **瓦片与图集规范**：统一 16×16 网格、锚点、留白（atlas 防渗色）、命名（`crop_carrot_stage_3.png`）、导出格式与过滤设置。
3. **地图生产流水线**：TileSet 地形集合（草地/耕地/水/道路）、装饰层、碰撞层、物件层（Y-Sort）、出生点与区域标记。地图之间用统一约定拼装。
4. **音频**：环境音、动作音效、UI 音效、BGM 各需几条；统一响度（约 -16 LUFS 背景、-12 峰值），音量分组（Master/Music/SFX），可单独调节。
5. **动画规范**：帧率（如 8–10 fps 像素动画）、循环标记、命名与目录、动画状态与代码状态的映射表。
6. **内容评审**：每批内容产出后做一次"风格一致性"检查（调色板、描边、密度），不一致的当场返工而不是攒着。
7. **缺口的合规对策**：字体用可商用像素字体并记录许可证；音效注明来源与许可（CC0 也写）；所有第三方素材建立 `CREDITS.md`。

#### 产出物

- 完整地图与瓦片资源
- 作物/物品/动物/UI 全套图形
- 音频库与音量分组
- `CREDITS.md`（素材来源与许可）
- 内容清单（全部勾选状态）

#### 阶段门（Gate 5）

- [ ] 内容清单 100% 完成，无占位图形
- [ ] 全部素材有明确许可证记录
- [ ] 所有瓦片对齐 16×16 网格，无半像素偏移
- [ ] 音频响度一致，无爆音，音量分组可用
- [ ] 每张地图能独立加载不报错

#### 常见坑

- 边做系统边找素材，导致美术风格反复推翻，已做的界面全部返工。
- 忽略留白与过滤设置，导出后瓦片边缘出现缝隙/渗色。
- 音效来源不明，发布前被迫重做。

---

### 阶段 6：系统开发与整合

**目标**：把设计里的每个系统实现并**接起来**，形成完整游戏流程。

#### 必做事项

1. **按依赖顺序开发**：底层（移动/交互/地形）→ 玩法（种田/动物/经济）→ 包装（UI/音频/引导）→ 元层（存档/成就/设置）。
2. **系统间契约先行**：先定数据接口与信号，再各写各的。例：`Inventory.add_item(id, count) -> int`（返回实际加入数量，处理溢出）。
3. **状态管理集中化**：游戏状态（当前天、金币、背包、已解锁内容）只允许一处修改，其他模块只读或发请求。
4. **UI 与逻辑分离**：UI 订阅信号刷新，不反向操作数据；背包/商店/结算都通过同一套接口。
5. **完整流程串通**：新游戏 → 教学 → 日常循环 → 睡觉结算 → 存档 → 读档 → 退出，一次通跑不中断。
6. **边做边测**：每完成一个系统就跑一次主流程回归，不留"最后一起测"。
7. **技术债登记**：为赶进度写的临时方案单独记一条，写清替换条件（例如"商店写死 3 个物品，等物品表稳定后改数据驱动"）。

#### 产出物

- 全部玩法系统与 UI
- 存档/读档与设置菜单
- 技术债清单（含替换条件）
- 集成后的可玩构建

#### 阶段门（Gate 6）

- [ ] 主流程可从头玩到第 7 天解锁节点，无卡死
- [ ] 所有界面可正常打开/关闭，不重叠、不残留输入
- [ ] 存档在任意时刻退出后能正确恢复
- [ ] 没有 `get_node` 的跨场景硬引用
- [ ] 技术债清单每条都有替换条件，且不影响发布

#### 常见坑

- 各系统各自维护一份"金币/时间"，最后数据不一致。
- UI 直接改存档数据，导致读档后界面不刷新。
- 只有到最后才把系统接起来，发现接口对不上，需要大改。

### 阶段 7：测试与 QA

**目标**：把"能玩"变成"稳定地能玩"。测试贯穿全程，末期集中回归。

#### 必做事项

1. **测试分层**：
   - 单元测试（纯逻辑：作物阶段推进、经济计算、背包溢出）——可用 GUT 等框架
   - 集成测试（存读档往返、一天结算、商店买卖）
   - 手动功能测试（用例表逐条执行）
   - 探索性测试（故意乱操作：连点、快速开关界面、边浇水边睡觉）
   - 性能测试（大量作物/掉落物、长时间挂机内存增长）
2. **用例表**：每个系统 5–15 条，写"前置条件 → 操作 → 期望结果"。期望结果必须可观察。
3. **bug 分级与流程**：P0（崩溃/存档损坏/进度阻塞）立即修；P1（功能错误）本迭代修；P2（体验问题）排期；P3（打磨）存档待办。每条 bug 记录复现步骤、环境、构建版本。
4. **回归测试**：修完 bug 必跑关联用例；每次发版前跑全量 P0/P1 用例。
5. **兼容性**：不同分辨率/窗口模式、不同存档版本、以及目标平台的最低配置。
6. **可访问性与本地化预检**：字号可读性、色盲友好（耕地与草地不能只靠色相区分）、文本不硬编码、字体支持目标语言字符。

#### 产出物

- `docs/05-测试与发布检查表.md` 中的用例表
- bug 库与回归记录
- 性能测试报告（帧率、内存、加载时间）
- 稳定的候选发布版本（RC）

#### 阶段门（Gate 7）

- [ ] P0、P1 清零；P2 有明确处理结论
- [ ] 全量用例通过且记录在案
- [ ] 连续游玩 60 分钟无崩溃、无明显内存增长
- [ ] 控制台无 `SCRIPT ERROR`
- [ ] 三种以上分辨率下 UI 不破版

#### 常见坑

- 测试只测"正常路径"，异常路径（背包满、金币不足、存档写到一半退出）全崩。
- 存档兼容性没测：自己的旧档在新版本读不了。
- bug 只口头记，修完不复测，出现"修好一个坏两个"。

### 阶段 8：平衡、打磨与引导

**目标**：让玩家不需要说明书也能玩懂，并且玩得舒服。

#### 必做事项

1. **数值校准**：用"第 1 / 3 / 7 / 14 天"四个节点定义玩家应有状态（金币、田块数、作物种类、游玩时长），实际跑数据对比调整。避免前期无聊（等太久）或后期通胀（钱没处花）。
2. **节奏曲线**：每 2–3 分钟一个小反馈（收获、金币音、解锁提示），每 10–15 分钟一个中反馈（新作物、新田块），每 30 分钟一个大节点（新工具/新区域）。
3. **反馈打磨（juice）**：命中音效、粒子和弹跳、数字飘字、屏幕轻微震动、动画曲线（先快后慢）、输入缓冲与动作取消窗口。**只加不干扰操作的部分。**
4. **引导设计**：分三步——环境提示（地里有闪烁的种子）、最小教学（第一次锄地给一行提示）、可查帮助（按键速查）。禁止大段文字弹窗。
5. **可读性**：交互目标高亮、可交互与不可交互的视觉区分、UI 对比度、重要提示不靠颜色单独表达。
6. **设置项**：音量、窗口模式、语言、按键重绑定（至少移动与交互）、重置存档。
7. **外部试玩**：5 人以上盲玩，记录"第一次卡住的时间点""误解的规则""想当然的操作"，逐条决定改或不改。

#### 产出物

- 数值终版（写回 GDD 并注明实测依据）
- 引导流程与帮助界面
- 打磨清单（勾选状态）
- 外部试玩报告与处理结论

#### 阶段门（Gate 8）

- [ ] 5 名陌生玩家中至少 4 人能独立完成第一天的完整循环
- [ ] 无人询问"我现在该干什么"超过一次
- [ ] 每个操作都有视觉与听觉反馈
- [ ] 数值曲线在四个节点上符合设计预期
- [ ] 所有设置项生效且能持久化

#### 常见坑

- 靠弹窗教玩法，玩家关闭后仍不会。
- 无限加特效导致操作延迟、画面噪音。
- 只让自己和熟人试玩，误判"很简单"。

### 阶段 9：发布准备

**目标**：让游戏能被安装、被找到、被购买/下载，且发布可回滚。

#### 必做事项

1. **导出配置**：导出预设（Windows/Linux/Web 视目标）、图标、版本号、公司/产品名、启动画面、签名（如需）。
2. **发布构建验证**：在**干净环境**（无编辑器、无开发缓存）安装运行，验证存档路径可写、配置文件生成位置正确、无编辑器专属依赖。
3. **商店/分发页**：标题、一句话卖点、截图（至少 4 张，含玩法与 UI）、GIF/短视频、玩法说明、系统需求、标签。素材必须来自正式版本。
4. **合规与法务**：第三方素材许可清单（`CREDITS.md`）、字体许可、隐私声明（若收集数据）、平台年龄分级。
5. **发布检查表**：版本号一致、无调试作弊键残留、无测试存档、日志不写入用户目录垃圾、无 `print` 刷屏、无未授权素材。
6. **回滚与热修预案**：保留上一版构建、明确热修流程、准备"已知问题"公告模板。
7. **发布节奏**：先小范围（朋友/社区）灰度 3–7 天，收集崩溃与存档问题，再正式公开。

#### 产出物

- 可分发构建包
- 商店页素材与文案
- `CREDITS.md` 与许可证清单
- `docs/05-测试与发布检查表.md` 勾选完成的发布检查表
- 灰度反馈与热修记录

#### 阶段门（Gate 9）

- [ ] 干净机器上安装 → 游玩 → 存档 → 重启继续，全流程通过
- [ ] 版本号、图标、商店文案与实际内容一致
- [ ] 所有第三方素材许可可查
- [ ] 调试功能与作弊键全部关闭
- [ ] 有已验证的上一版构建可回滚

#### 常见坑

- 只在开发机上测，发布后才发现存档目录不可写。
- 截图用编辑器画面或旧版本，和实际游戏不一致。
- 忘记移除调试快捷键，玩家一键刷满金币。

### 阶段 10：上线后运营与复盘

**目标**：用真实反馈驱动迭代，同时避免被反馈带偏方向。

#### 必做事项

1. **反馈渠道**：一个明确的 bug/建议入口，分类收集（崩溃、存档、玩法、平衡、内容需求）。
2. **数据（若有）**：留存、卡点、崩溃率；无数据时用社区讨论与评测高频词代替。**只采必要数据并声明。**
3. **热修节奏**：P0 24 小时内、P1 一周内；每次热修都要更新版本号并记录变更。
4. **更新计划**：区分"修复"与"内容"，内容更新按阶段 1 的范围流程重走一遍（设计 → 原型 → 验证），不要直接堆。
5. **技术债偿还**：按阶段 6 登记的替换条件逐条处理，优先处理阻碍新内容的债。
6. **项目复盘**：实际工期 vs 估算、哪些设计被玩家无视、哪些决策后悔、下次如何避免。**写成文档，这是下一个项目最大的资产。**

#### 产出物

- 变更日志（Changelog）
- 热修与更新记录
- 反馈分类统计与处理结论
- 项目复盘文档

#### 常见坑

- 被少数高嗓门玩家牵着改核心设计。
- 只加内容不修底层问题，越更新越难改。
- 不做复盘，下一个项目重复同样的估算错误。

### 横切关注点（每个阶段都要做）

| 关注点 | 做法 |

| 6 | 种田、时间与睡觉结算、经济商店、背包与箱子、鸡舍产蛋、UI（HUD/背包/商店/结算）、存档设置 | 主流程连玩 7 天不中断 |
| 7 | 逻辑单测（作物推进、经济、背包溢出）+ 手动用例（存读档、满背包、金币不足、切分辨率）+ 60 分钟挂机 | P0/P1 清零 |

| 10 | 社区灰度 3–7 天、热修、按复盘结论规划下一批内容 | 复盘文档完成 |

#### 当前已知的阻塞项（开始阶段 2 前必须处理）

- `project.godot` 未设置 `rendering/textures/canvas_textures/default_texture_filter`，默认线性过滤会让 16×16 像素画发糊，需改为 Nearest。
- 未设定基准分辨率与像素对齐策略，需与 `display/window/stretch/*` 现有 `canvas_items` + `expand` 组合一起确认。
- `scenes/main.tscn` 目前是占位场景（菱形 `Polygon2D` + 方向键移动），无 TileMap、无 AnimatedSprite2D、无存档。
- `assets/` 下无任何 TileSet / `.tres` 资源，地形与图集需从零搭建。
- 输入映射仅有内置 `ui_*`，需新增移动、交互、使用工具、打开背包等动作。
- 无音频、无像素字体、无 UI 素材、无 NPC 立绘，需在阶段 5 前确定来源。

## 可玩版本演进路线图（每版游戏长什么样）

配套文档：`01-游戏开发全流程.md` 讲"每个阶段该做什么事"，本文讲"每个版本做出来是什么样、能玩到什么程度"，具体技术方案对照见 `03-参考项目技术对照.md`。

**核心原则：地图先行。** 地图不是美术背景，它是坐标基准：相机范围、碰撞边界、交互单元（哪一格）、存档单元（哪块地种了什么）全部以它为基础。地图先立住，后面的行走、耕地、种植、动物、存档都是往同一套格子上叠，改一次不会推翻全局。

### 全局画面基准（V0.1 就定死，后面不改）

| 项 | 值 | 理由 |
| --- | --- | --- |
| 瓦片尺寸 | 16×16 px | 现有素材全部按此网格 |
| 基准视口 | 320×180 px（显示 20×11.25 格） | 1280×720 恰好 4 倍、1920×1080 恰好 6 倍，整数缩放不糊 |
| 窗口 | 1280×720，可拉伸 | `canvas_items` + `expand` 已配置 |
| 贴图过滤 | Nearest（`rendering/textures/canvas_textures/default_texture_filter = 0`） | 当前未设置，默认线性会让像素发糊，**必须改** |

#### 遮挡淡出（2026-11-02 追加）

**问题**：Y 排序只保证"谁在前谁在后"，角色走到树冠或屋顶后面时会被完整遮住，玩家看不到自己。

**方案**：`scripts/world/occlusion_fader.gd` 挂在 `World` 上，每物理帧检查每个道具，**同时满足**两个条件才淡出：

1. 道具脚底 y > 角色脚底 y（道具被排在前面，会盖住角色）；
2. 角色的**脚底点**落在道具遮挡框内（遮挡框左右各内缩 4px）。

> 判定规则改过一次：最初用"贴图包围盒相交"，结果角色只是站在房子**侧面**、身体蹭到墙面也会淡出。改成脚底点 + 水平内缩后，只有角色真正站进道具脚下/身后才命中，侧面经过不再误判。

命中时用 `Tween` 把 `modulate:a` 补到 0.55（0.12s），离开后补回 1.0。包围盒在 `_ready` 缓存一次（道具不移动），只在目标透明度变化时重建 Tween。

**同时修正**：小屋碰撞体原先只覆盖底部 40×14，角色能从侧面走进房屋内部；已改为 40×40（覆盖建筑轮廓），角色只能站在门外、不能穿进屋里。

**验证**：站在小屋背后 → 小屋降到 55% 透明度，角色可见；站在树后 → 树冠变半透明，角色可见；站在道具**侧面** → 保持 100% 不透明；走到道具前方 → 透明度恢复 100%。`smoke_check` 增加"World 必须挂载 occlusion_fader"的回归检查。

#### 贴图取区修正（2026-11-02 追加）

**问题**：地图上出现"侧翻的树"（绿色树冠连着棕色树桩横躺在地上）。

**原因**：`basic_grass_biom_things.png` 的第 4 行第 0–1 列是**倒下的树**，与第 2 行第 5 列的原木很像，取区时选中了前者。

**修正**：`log_pile.tscn`（区域 `(36,64,32,16)` = 倒树）删除，新建 `scenes/world/props/log.tscn` 使用真正的原木 `region_rect = Rect2(80, 32, 16, 16)`，`offset.y = -5` 让原木底边贴地，碰撞 14×8。

| 类型 | 取法 | 例子 | 原因 |
| --- | --- | --- | --- |
| **建筑** | 只覆盖**墙体和台阶**（落地部分） | 小屋 `40×24` @ `(0,-12)`，贴图 48×48 | 屋顶属于"空中"，其屏幕位置对应的是房子背后的地面；如果按整张贴图挡，会在地图北侧形成一圈看不见的墙，角色被推得离房子很远 |
| **矮物件** | 只覆盖**底部落地部分** | 树用半径 4–5 的圆、灌木/石头/原木用底部矩形 | 树干很细，树冠悬空；只挡树根才能贴着树走 |

屋顶怎么办：角色走到房子背后时会进入屋顶的屏幕范围，此时由 `occlusion_fader` 把房子淡到 55%，角色隔着半透明屋顶可见——这就是"走到房子后面"的标准表现。

小屋碰撞体演进：`40×14`（会穿墙进屋）→ `40×40`（挡住 2.5 格，离房子太远）→ `44×48`（与贴图等高，北侧出现无形墙，角色被顶到屋顶上方）→ **`40×24`（只挡落地墙体，角色能正常贴到房子背后）**。

**设计决定**

1. **每格独立方块，不做自动连边**：第一版按九宫格邻接拼合，单格凸起会渲染成"城垛"（见开发过程截图），而素材里并没有"单格独立地块"图。改为每格统一铺地格后，锄出来永远是规整矩形，行为可预测。代价是失去圆角美观，等有独立地块素材再换。
2. **地块绘制权收归 Tiller**：原先苗圃由生成器画在 `Overlay` 层，玩家新锄的地却在 `Soil` 层，两处逻辑容易分叉。现在统一由 Tiller 画在 `Soil`/`Watered` 层。
3. **湿土用调制而非新贴图**：现有素材没有"湿土"图，用同款瓦片叠一层压暗的 `Watered` 层实现，效果可读且零美术成本。
4. **铺地格用坐标哈希挑碎石变体**：`(x*73856093) ^ (y*19349663)`，保证同一格每次重画结果一致，不会闪烁。

**与计划的差异**

1. **工具挥动动画未做**：`basic_charakter_actions.png`（96×576，6×36 格）的具体分帧规则还没验证，先不做；锄地/浇水目前只有地块变化反馈。留到 V0.9 统一做动作与音效。
2. **种子袋槽位为占位**：`seeds` 工具已进入工具栏但使用无效（V0.5 接播种）。
3. **未做"无效操作反馈"**：目前无效格只是隐藏高亮框，没有音效或提示文字，等 V0.9 的反馈层统一补。

**验证**

- 实机：鼠标左键锄地生成规整方块耕地、数字键切换工具、切到水壶点左键浇水后变深、高亮框随朝向移动、锄完该格后高亮消失（不可再锄）、工具栏高亮跟随切换
- `smoke_check` 增加耕地相关断言（Soil/Watered 层、Tiller 脚本、Cursor 子节点、`mouse_use` 等动作存在性）PASS
- 控制台无 `SCRIPT ERROR` / `ERROR`

#### 观感与 UI 调整（2026-11-02 追加）

**1. 耕地太突兀**

素材的耕地底色 `(232,207,166)` 明显亮于草地，一整块铺上去像贴纸。处理：

- `Soil` 层 `modulate = (0.88, 0.82, 0.72)`，把亮度压到接近草地的明度区间
- `Watered` 层同步改为 `(0.70, 0.62, 0.54)`，保持"湿土更暗"的层级关系
- 碎石细节变体比例从 30% 提到 50%，地块不再是一大片纯色

**2. 工具栏不像像素游戏**

原来用 `PanelContainer` 默认主题（深灰圆角 + 粗体无衬线字母），和 16px 像素画完全不是一套语言。改为：

- 槽位用 `StyleBoxFlat` 手写：不透明深色底 + 1px 米色描边 + 直角，接近像素 UI 的观感
- 图标改用素材自带的 `assets/game/characters/tools.png`（16×16）：锄头 `(0,4)`、水壶 `(0,0)`、种子袋 `(3,0)`，用 `AtlasTexture` 裁切、`STRETCH_KEEP_CENTERED` 保证像素对齐
- 选中态仍用 `modulate` 区分（1.0 / 0.45）

**3. 角色与地块的层级**

- 玩家在 `World`（z 10）下，`Soil` 为 z 5、`Watered` 为 z 6，角色本来就画在地块之上，实测站在苗圃上角色完整可见。
- 但发现真正的层级 bug：高亮框 `Cursor` 原为 z 0，**低于** Soil/Watered，高亮落到耕地上会被地面盖住。已把 `Cursor` 提到 `z_index = 20`。

#### 开垦限制、动作表现与边界过渡（2026-11-02 追加）

**1. 开垦不能再随处点**

规则改为：目标格必须**紧邻已有耕地**（上下左右任意一格），且落在 `TILLABLE` 范围内。初始 4 块苗圃就是扩张起点，耕地会顺着边缘长出去，不会在草地中间凭空挖出一块。

- `_is_tillable()`：范围判定 + 已开垦判定 + 四邻至少一格是耕地
- 浇水本来就是"只对已开垦且未浇水的格子生效"，无需改动

**2. 使用工具的动作**

角色进入 `is_acting` 状态：锁移动、锁工具切换，总时长 0.34s，**命中帧（0.15s）才真正改地形**，不是点击瞬间生效。表现由三部分组成：

- 角色朝面向方向小幅前冲再回位（`_play_action_motion`）
- 目标格上方出现工具图标并做 0.16s 的下挥弧线，随后淡出（`_play_tool_swing`）
- 命中时喷 8 颗 CPUParticles2D 粒子（锄地是土黄、浇水是水蓝）

**3. 耕地边界过渡**

新增 `SoilFringe` 层 + 运行时生成的过渡图集：四张 16×16 的渐隐色带（贴耕地一侧最实、向外 6px 淡出，带轻微噪点）。每次地块变化后重算 3×3 邻域，空地上有耕地的方向就撒一层色带。效果是把"硬边"变成一圈柔和的土壤过渡。

> 试过用散点土屑，但 4 倍缩放下会像"草刺"，改成色带后才读得出是过渡。

**仍缺的素材（需要补充）**

1. **角色动作帧**：`basic_charakter_actions.png` 是 96×576，按 48×48 分块是 2 列 × 12 行共 24 帧，但**没有说明每帧属于哪个方向/哪个工具/第几帧**，无法可靠接入。需要：四方向 × 锄地/浇水各 3–4 帧的图集（或告诉我这张图的行列含义）。
2. **草地↔耕地过渡瓦片**：现有素材只有 blob 的角/边（整块草地色），没有任意形状的过渡，所以只能用程序生成的色带近似。若能提供一套 16px 过渡瓦片（4 向 + 4 角），可换成正规瓦片过渡。
3. **湿土贴图**（可选）：目前靠压暗 `modulate` 表现，若有专门的湿土贴图会更清楚。

### V0.7 能长期玩（时间、睡觉、存档）

**一句话**：有白天黑夜和天数，睡觉进入下一天，退出游戏进度不丢。

#### 画面

- 左上角显示"第 N 天 06:00"，时间随游玩缓慢推进（例如 1 游戏小时 = 30 秒）。
- 到点后画面轻微变暗（傍晚/夜晚），角色可继续活动但作物不长。
- 走到床边/回屋按睡觉，弹出结算画面：今天收获、今天收入、进入第 N+1 天。
- 主菜单/暂停菜单：继续、新游戏、设置、退出。

#### 玩家能做什么

- 看时间与天数，感受作息
- 睡觉推进到下一天，作物统一结算生长
- 随时暂停、存档、读档、返回主菜单
- 关掉游戏再打开，金币、地形、作物阶段、背包全部恢复

#### 新增资源与文件

| 类型 | 路径 | 说明 |
| --- | --- | --- |
| 时间系统 | `scripts/systems/time_system.gd`（Autoload 或单例节点） | 时/分/天、速度倍率、`day_changed` 信号 |
| 存档 | `scripts/systems/save_system.gd` | 序列化：天数、金币、背包、`soil_grid`（地形+浇水+作物阶段）、玩家位置 |
| 存档格式 | `user://save_1.json`（或 `ConfigFile`） | 顶层带 `version` 字段，读档缺字段走默认值 |
| 结算 UI | `scenes/ui/day_summary.tscn` | 日报 + 确认进入下一天 |
| 主菜单 | `scenes/ui/main_menu.tscn` | 新游戏 / 继续 / 设置 / 退出 |
| 暂停 | `scenes/ui/pause_menu.tscn` | `Esc` 打开，暂停游戏树 |

#### 验收标准

- [ ] 睡觉后作物按"是否浇过水"统一推进，天数 +1
- [ ] 任何时刻（耕作中、商店打开时除外）退出再进入，进度完全一致
- [ ] 存档带版本号；旧档缺新字段时能读、用默认值，不崩
- [ ] 存档文件损坏时不崩溃，提示"存档损坏"并允许新游戏
- [ ] 暂停时游戏内时间与动画停止，恢复后继续
- [ ] 从主菜单进入游戏到退出，主流程无卡死

#### 明确不做

动物、引导、音频打磨（下一阶段）。

#### 实际记录（2026-11-03，时间与存档已完成）

| 内容 | 实现 |
| --- | --- |
| 时间系统 | `scripts/systems/time_system.gd`：第 N 天 06:00 起、26:00 收工、1 现实秒 = 4 游戏分钟、`time_changed` / `day_started` / `day_over` |
| 昼夜 | `DayNightTint`（`CanvasModulate`）：17:00 渐暗、21:00 最深，只影响世界不影响 UI |

| 存档 | `scripts/systems/save_system.gd`：`user://save_1.json`，含版本号、时间、金币、背包、耕地、作物阶段、玩家位置；睡觉与关窗口时自动存，启动自动读；坏档隔离为 `.broken` |

> 并区分白天/晚上——06:00–17:59 上床只是小睡到 20:00（不换天、不结算作物），18:00 之后才过夜进入下一天。

### V0.8 有第二条产出线（动物）

**一句话**：鸡会自己走动，每天下一个蛋，捡蛋卖钱。

#### 画面

- 鸡舍前有 1–3 只鸡随机踱步，偶尔啄地；靠近会小幅避让。

- 捡蛋时 HUD 背包条里蛋的数量 +1。

#### 玩家能做什么

- 走到蛋上按交互键拾取
- 卖蛋（复用商店）获得第二条收入
- 观察到"鸡每天产一个蛋"的稳定节奏

#### 新增资源与文件

| 类型 | 路径 | 说明 |
| --- | --- | --- |
| 动物 | `scenes/world/chicken.tscn` + `scripts/world/chicken.gd` | 简单游走状态机（在鸡舍周围范围内随机点移动） |

- [ ] 鸡在限定区域内游走，不会走出围栏、不会卡进建筑
- [ ] 每天最多产 1 个蛋，睡觉后必产，蛋不重复堆叠在同一格

#### 目标系统（2026-11-03 追加，原计划外）

原路线图把"任务系统"排在 V1.0 之后，实际做下来发现：**只有两种作物时，第 3 天之后玩家就没有新东西可追**。所以提前补了两层目标：

| 内容 | 实现 |
| --- | --- |
| 日订单 | `Systems/Orders`：每天一张，从已解锁农产品里挑，报酬 = 卖价 × 数量 × 1.7；木屋旁麻袋（`OrderBin`）按 `E` 交 |
| 社区中心 | `Systems/CommunityCenter`：三阶段上缴（木材纤维 → 胡萝卜鸡蛋 → 小麦石头），每段发奖金并解锁新种子；建筑在左下 `(120,416)` |
| 种子解锁 | `ItemData.unlock_stage` + 商店过滤；没解锁的商品在买入列表末尾提示「还有 N 种货没解锁」 |
| 新作物 | 萝卜（阶段 1 解锁，卖 50）、小麦（阶段 2 解锁，卖 80），素材原本就有 |
| 换种子 | 拿种子袋时 `Q / E` 在几种种子之间切换（之前只能种背包里第一种） |
| 存档 | `community.stage` 与 `orders` 两个字段；读档先恢复阶段再恢复订单 |

详细设计见 [订单与社区中心](02-系统设计.md#订单与社区中心)，自检 `tools/check/check_goals.gd`。

#### 体力与天气（2026-11-03 追加）

订单解决了"没事干"，但干活仍然没有代价、天天都是晴天。补上两个每天要做的取舍：

| 内容 | 实现 |
| --- | --- |
| 体力 | `Systems/Stamina`：上限 100，锄地 4 / 浇水 2 / 播种 2 / 收获 2 / 砍树 8 / 碎石 6，睡觉回满；不够时 `can_use()` 直接拦住并提示"回屋睡一觉" |
| 天气 | `Systems/Weather`：晴 50 / 阴 30 / 雨 20，`time_changed` 时按天重掷；雨天等于把所有作物浇了，地也保持湿润 |
| 画面 | 天气色乘法叠在昼夜色上（雨天偏蓝）；HUD 时间条加天气字，右下角一根竖向体力条 |
| 存档 | `stamina`、`weather` 两个字段；天气要在时间之后恢复 |
| 可重复测试 | `weather.lock(&"sunny")` 固定天气，避免"没浇水不长"的断言随机失败 |

详细设计见 [体力与天气](02-系统设计.md#体力与天气)，自检 `tools/check/check_survival.gd`。

## 参考项目技术对照：KimiLook（Unity《麦田物语》）

参考仓库：https://github.com/yuyucode/KimiLook （MIT，35 stars）
性质：Unity + C# 的 2D 农场模拟经营**教学工程 + 中文笔记**，源自 Unity 中国官方课程《麦田物语》（MFarm）。不是成品游戏，价值在于"2D 农场关键子系统的实现速查表"。

| Pixel Perfect Camera + Cinemachine 跟随/边界 | V0.2 玩家与镜头 | 高（概念完全一致） |
| Transparency Sort Mode = Custom Axis(0,1,0) + Pivot 在脚底 | V0.3 遮挡排序 | 高 |
| Tilemap / Tile Palette / Rule Tile / Sprite Atlas 去缝 | V0.1 地图 | 高 |
| Tilemap Collider + Composite Collider + Custom Physics Shape | V0.3 碰撞 | 高 |
| ScriptableObject 物品表（`ItemDataList_SO`） | V0.6 商店/物品 | 高 |
| 静态事件总线 `EventHandler` + 单例 `InventoryManager` | V0.6 背包 | 中（Godot 用信号） |
| 背包 UI 事件刷新、拖拽（`IDropHandler`） | V0.6 / V1.0 | 中 |
| Animator Blend Tree + Override Controller 换装 | V0.2 / V1.0 | 中（Godot 用 SpriteFrames） |
| DOTween 补间 | V1.0 反馈打磨 | 中（Godot 内置 Tween） |
| 存档、时间/日历、作物生长、经济、动物 | 无（课程没做） | 无，需自行设计（见 `02` 文档 V0.5–V0.8） |

**关键判断**：它强在"引擎技巧 + UI 数据流"，弱在"进度的长线系统"。而农场游戏的核心恰恰是后者。所以它只能当**技术参考**，不能当**设计参考**。

### 二、技术方案逐项对照（Unity → Godot 4）

#### 1. 像素完美与分辨率

| 它 | 我们 | 落地要点 |
| --- | --- | --- |
| Pixel Perfect Camera（Assets Pixels Per Unit = 16，Reference Resolution） | 基准视口 320×180 + `stretch/mode=canvas_items` | 已有 `canvas_items`，需补 `display/window/size/viewport_width=320`、`viewport_height=180` |
| Filter Mode = Point | `rendering/textures/canvas_textures/default_texture_filter = 0`（Nearest） | **当前缺失，必改**，否则整套像素画发糊 |
| Ortho Size 9 | 正交相机，缩放由视口决定，不再手动调 | 320×180 已把 16px 瓦片放大到合适大小，不需要额外 zoom |

> 注意：不要在 Godot 里再把 Camera2D 的 `zoom` 设成 2、3 这种值，会和窗口拉伸打架。缩放交给窗口拉伸，相机只负责位置。

#### 2. 摄像机跟随与边界

| 它 | 我们 |
| --- | --- |
| Cinemachine Virtual Camera + Body 阻尼 + Confiner2D 限位，`SwitchBounds` 换边界 | `Camera2D` 的 `position_smoothing_enabled` + `limit_left/right/top/bottom` |

落地要点：
- 相机挂在玩家下会跟着动画抖动，**相机应作为独立节点，在 `_physics_process` 里跟随玩家的脚底位置**。
- `limit_*` 用地图像素边界填死（40×30 格 = 0..640 / 0..480），场景切换时更新这四个值。这就是它的 `SwitchBounds` 的等价物，不需要额外脚本。
- 平滑系数从 `8.0` 起调（`position_smoothing_speed`），过高会跟不动，过低会飘。

#### 3. Y 轴遮挡排序（最容易踩坑的一项）

| 它 | 我们 |
| --- | --- |
| Project Settings → Graphics → Transparency Sort Mode = Custom Axis，Axis = (0,1,0) | `CanvasItem.y_sort_enabled` + `y_sort_origin` |
| Sprite Sort Point = Pivot，Pivot 设在脚底 | `Sprite2D.offset` 让贴图以脚底为原点；`y_sort_origin` 设为 0（脚底） |
| Sorting Group 让父子整体排序 | 父节点 `y_sort_enabled = true`，子节点不单独破排序 |

落地要点：
- 排序容器的父节点（如"物件层" `Node2D`）开启 `y_sort_enabled`，其所有子节点按**自身 y 坐标**排序。
- 精灵的锚点必须是脚底中心，否则会出现"人物半截插进屋顶"。
- `TileMapLayer` 同样支持 `y_sort_enabled`，但地形层不要开，只有物件层开。
- 树之类的"底部小、上方大"的物件，其 y 坐标用树根位置，不是图片中心。

#### 4. Tilemap 与瓦片缝隙

| 它 | 我们 |
| --- | --- |
| Tile Palette 绘制；Rule Tile 自动连边；Random Brush 随机变体 | `TileSet` 的 **Terrain Sets（地形集）** 做自动过渡；`TileMapLayer` 绘制 |
| Sprite Atlas：Filter = Point、Compression = None、**加大 Padding** 解决瓦片间缝隙 | 单张 PNG 直接做图集，关键在**过滤设 Nearest + 不做压缩 + 关闭 mipmap**；如打图集则必须留 2px padding |
| Tilemap Collider 2D + Composite Collider 2D（Used By Composite） | `TileMapLayer` 设置 `physics_layers` + 图块 `physics` 多边形；碰撞合并由 TileSet 物理层自动处理 |

落地要点：
- 我们的 `grass.png`(176×112)、`tilled_dirt*.png`(176×112) 是 11×7 格，属于"3×3 极简 + 变体"布局，用 Terrain Sets 的 3×3 模式即可，不必强上 47 位全掩码。
- `bitmask_references_1/2.png` 是**参考图**（说明素材对应的掩码组合），不是当瓦片用的图，别拖进 TileSet。
- 草地与耕地的交界要"耕地叠在草地之上"，用两个 `TileMapLayer`：地面层（草地/水/路）+ 覆盖层（耕地），避免互相覆盖冲突。
- 瓦片边缘出现 1px 缝隙时，优先查：过滤是否为 Nearest、是否有 mipmap、图集是否留 padding，**不要**去改图块尺寸。

#### 5. 数据驱动（ScriptableObject → Resource）

| 它 | 我们 |
| --- | --- |
| `[CreateAssetMenu]` 生成 `ItemDataList_SO`，Inspector 编辑物品表 | `class_name CropData extends Resource` + `@export` 字段 + `.tres` 文件 |
| `ItemDetails` / `InventoryItem` 结构体 | 自定义 `Resource` 或 `RefCounted` 数据类 |

落地要点：
- 用 Godot 4 的 `@export` 暴露字段，字段上写 `@export_group` 分组，Inspector 体验接近 SO。
- 资源文件放 `data/`（`data/crops/`、`data/items/`），路径固定，代码只 `preload` 目录式清单或按 id 查表。
- **它这里有个已知缺陷**：`AddItem` 中"背包无该物品且无空位"的分支未处理（作者自标 TODO）。我们的对应做法是 `inventory.add_item(id, count) -> int` **返回实际存入数量**，永不静默丢弃。

#### 6. 事件驱动 + 单例 → 信号 + Autoload

| 它 | 我们 |
| --- | --- |
| `public static event Action<...> OnUpdateInventoryUI` + `EventHandler.Call...` 广播 | Autoload `EventBus`（`Node`）里的 `signal inventory_changed(slots)`，或直接 `InventorySystem.inventory_changed` |
| `Singleton<InventoryManager>` 管理器 | Autoload（`GameState`、`InventorySystem`、`TimeSystem`、`SaveSystem`） |
| UI 在 `OnEnable` 订阅、`OnDisable` 退订 | `_ready` / `_enter_tree` 里 `connect`，`_exit_tree` 里 `disconnect`（或用 `CONNECT_ONE_SHOT`） |

落地要点：
- Godot 信号天然解耦，不需要自造静态事件总线类；但**跨系统通信集中在一处**的思路要保留：`EventBus` 只放"全局广播"（`day_changed`、`item_obtained`、`gold_changed`），系统内部事件用各自信号。
- **它的另一个隐患**：静态事件订阅忘记退订会导致重复刷新甚至空引用。Godot 里同样存在（节点释放后信号仍连到旧回调）。规则：跨节点连接一律在 `_exit_tree` 断开，或 `connect` 时传 `CONNECT_ONE_SHOT`/使用 `is_instance_valid` 防护。
- 单例不要做成"上帝对象"。它在 `InventoryManager` 里同时管数据、查容量、改数据、通知 UI，我们拆成：`InventorySystem`（数据）+ `inventory_bar.tscn`（只订阅刷新）。

#### 7. 动画

| 它 | 我们 |
| --- | --- |
| Animator：`idle` Blend Tree + `Walk Run`，`isMoving` 参数 | `AnimatedSprite2D` + `SpriteFrames`，或 `AnimationTree`（`StateMachine`） |
| Animator Override Controller 派生 Body/Hair/Arm 复用状态机 | 复用 `SpriteFrames`：同一套动画名 + 不同图集，换 `sprite_frames` 即可 |

落地要点：
- 我们只有一整套角色素材，V0.2 先用 `AnimatedSprite2D` + 动画名 `idle_down/walk_down/...` 十六个动画，够用。
- 真的有换装需求（V1.0 之后）再上 `AnimationTree`，别提前上。
- 走路动画播放速度与移动速度挂钩（`speed_scale`），否则慢走时脚底打滑。

#### 8. UI（UGUI 事件接口 → Control）

| 它 | 我们 |
| --- | --- |
| `IPointerClickHandler` 等一堆接口 | `Control` 的 `gui_input` / 内置 `pressed` 信号 |
| `IBeginDragHandler` / `IDragHandler` / `IDropHandler` | `_get_drag_data()` / `_can_drop_data()` / `_drop_data()` |
| 拖拽图片必须取消 `Raycast Target` | 拖拽预览用 `Control.mouse_filter = MOUSE_FILTER_IGNORE` |
| `LayoutRebuilder.ForceRebuildLayoutImmediate` 解决多列文本延迟 | `await get_tree().process_frame` 后读取尺寸；或 `Container.queue_sort()` |

落地要点：
- 背包格用 `Panel` + `TextureRect` + `Label`，格子里所有子节点设 `mouse_filter = IGNORE`，让点击落到格子上——和它"关掉 Raycast Target"是同一个坑。
- Godot 的 `_drop_data` 只会在 `_can_drop_data` 返回 `true` 时触发，判定条件要写全（格子可放、物品可堆叠、数量够）。

#### 9. 补间与反馈

| 它 | 我们 |
| --- | --- |
| DOTween（第三方） | 内置 `create_tween()`，无需插件 |

落地要点：金币飘字、收获弹跳、面板滑入全部用 `Tween`，不要手写 `_process` 插值；`Tween.kill()` 在节点释放前确保停止（或用 `tween.bind_node(self)` 自动处理）。

### 三、可以直接照搬的"做法"（与引擎无关）

1. **Pivot/锚点必须在脚底**——这是 Y 遮挡排序成立的前提，不是可选项。
2. **导入参数用统一预设**，不逐个手调。对应 Godot：`.import` 参数统一（过滤 Nearest、压缩关闭、mipmap 关闭），靠一次配置 + 复用。
3. **数据表与逻辑分离**：物品、作物、商品全部配置化，加内容不改代码。
4. **UI 通过事件刷新，不直接改数据**：UI 只订阅、只发请求。
5. **编辑器工具放在独立目录**：它用 `Assets/Editor`（不打包）；我们用 `addons/`（第三方）与 `tools/`（自研编辑脚本），业务代码不进 `addons/`。
6. **目录按职责分**：`Scenes / Scripts / Prefabs` → 我们的 `scenes / scripts / assets / data`。
7. **组件依赖显式声明**：它用 `[RequireComponent]`；Godot 用 `@onready` 强类型引用 + `assert` 校验，缺节点时早失败。

### 四、它踩过的坑（我们要提前避开）

| 它的问题 | 我们的对策 |
| --- | --- |
| `AddItem` 背包满时无处理（TODO） | `add_item()` 返回实际存入数，UI 提示"背包已满" |
| 静态事件订阅未退订 | 跨节点信号在 `_exit_tree` 断开；Autoload 信号只在 Autoload 内发 |
| 事件/单例职责过载（`InventoryManager` 什么都干） | 数据、规则、表现三层分开；Autoload 只放状态与广播 |
| 瓦片缝隙靠改图解决 | 先查过滤/压缩/padding 三件事，图不动 |
| 拖拽 UI 被自身图片挡住判定 | 子节点 `mouse_filter = IGNORE` |
| 学习工程无存档（进度一关就没） | 我们把存档提到 V0.7，且**格式带版本号**（这是它完全没有的部分） |

**许可证提醒**：仓库是 MIT，笔记与代码可参考；但 `Assets/` 里的美术可能来自课程/第三方，**不要直接取用其中图片或音频**。本项目继续使用现有 `assets/game/`（Sprout Lands 风格素材），并在 `CREDITS.md` 记录来源。

### 六、结论

- **可以学**：它的摄像机边界、Y 轴排序、Tilemap 去缝、ScriptableObject 配置化、事件驱动 UI 刷新，这五点直接对应我们 V0.1–V0.6 的关键实现，能少踩很多坑。
- **不要学**：单例什么都管、事件不设生命周期、背包满不处理、无存档设计——这些是教学工程的通病，农业模拟游戏会在第 7 天之后集中爆发。
- **它的空白正是我们的重点**：时间/日历、作物阶段、经济曲线、存档兼容、长线目标。这四块在 `02-可玩版本演进路线图.md` 的 V0.5–V0.8 里已经排好。
