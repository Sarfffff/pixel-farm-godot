# 架构与开发规范

生效日期：2026-11-04。适用 Godot 4 / GDScript 工程，以及后续参与本仓库的 agent。开发范围和阶段门槛仍以 `04-后续开发总纲.md` 为准。

文件放置和移动遵守 [目录与资源规范](07-目录与资源规范.md)。`scripts/README.md` 是业务代码索引，`assets/README.md` 是成品资源入口；目录移动需同步生成器与检查并保留 `.uid`/`.import`，运行 `python tools/maintenance/audit_project_layout.py`。

## 1 开发前与交付时必须执行

1. 先读根目录 `AGENTS.md`、本规范和后续开发总纲；检查工作区已有变更，保留其他开发中的代码与素材。
2. 说明本次修改的玩家行为、负责模块、输入输出、保存字段和兼容方式，再在最小边界实现。
3. 优先扩展已有端口、注册机制和 Resource 数据，不建立第二套金币、背包、时钟或存档。
4. 完成后使用隔离测试入口验证。检查退出码、断言、脚本错误和关键流程末尾，不以 PASS 字样单独认定成功。
5. 更新总纲任务状态和系统设计；自动检查与人工试玩分别记录。未完成真实输入验收的阶段不能标为已验收。
6. 交付说明必须包含：行为变化、存档影响、测试命令与结果、尚未验证的内容。

## 2 依赖方向与职责

```text
场景组合根 GameSession
    ├── 装配应用用例：DailyCycle、TradeService
    ├── 装配持久化：SnapshotRegistry → SaveStore
    └── 装配表现：ModalCoordinator、CoinFeedback

UI / 引擎适配 → 应用用例 → 领域状态与 Resource
持久化适配 → 编解码 / 迁移 / 存储端口
```

- `scripts/core/game_session.gd` 是场景组合根。跨模块的依赖注入、持久化参与者注册和事件接线集中在这里。
- 领域对象只维护自身事实与规则，不查找面板，不操作文件，不播放音效。
- 开发输入统一经 `platform/development_controls.gd` 适配，由组合根注入同步业务端口与运行条件。默认关闭、编辑器显式启用，导出 `farm_release` 标记始终拒绝；不能在Player、农田或View另加未受控跳天/发物资入口。开关不写玩家设置或存档。
- 应用用例协调一次完整操作，验证先于扣费，模型更新完成后才发成功事件。
- UI 负责输入、显示和反馈，通过用例改变数据；任务与引导订阅用例事件，不能依赖某个商店或对话面板存在。
- 引擎适配层可以使用节点组发现服务；长期依赖在初始化时绑定，核心状态机不依赖 SceneTree。不要把所有依赖塞进全局服务定位器。
- 持久化层只负责快照、迁移和存储，不调用会发奖励、掉落、收费或推进日期的玩法入口。

现有 `FarmTiller` 和 `FarmActivities` 保留兼容外观入口；新增独立行为应继续落入专门组件。农田编解码通过公开的数据参数工作，钓鱼计时通过 `FishingSession` 工作，不在这些旧入口重新堆积状态分支。

## 3 SOLID 的具体要求

### 3.1 选定的项目框架（2026-11-05）

采用**按业务模块组织的分层架构：应用服务 + MVP界面 + Godot节点组件**。这是代码组织和依赖契约，不引入第三方框架包。保留 `scripts/time`、`inventory`、`activities`、`animals` 等业务目录，避免为MVC字母再建立平行代码树。

| 角色 | 职责 | 当前落地 |
| --- | --- | --- |
| Model：状态、规则和配置 | 保存事实、校验条件、计算结果；不引用View或查找UI | Inventory、AnimalStateMachine、ResourceLedger、ProcessingSession、Resource配置 |
| 应用服务 | 协调一次完整操作，控制重入与事务，注入保存等端口 | TradeService、DailyCycle、RestService、StorageTransferService |
| Presenter | 将模型查询整理为只读显示数据，把View意图转换为服务调用 | DaySummaryPresenter、FarmActivitiesPresenter |
| View | 处理控件、焦点和输入，渲染快照，发意图信号 | DaySummary、FarmActivitiesPanel |
| Godot引擎适配 | 物理、动画、场景对象、相机和异步过场 | FarmAnimal、WorldRegions、RestController、FarmActivities兼容外观 |
| 组合根与持久化适配 | 装配依赖、注册入口与保存参与者，隔离文件存取 | GameSession、SnapshotRegistry、SaveStore |

依赖流为：`View意图 → Presenter/引擎控制器 → 应用服务 → Model`；更新后由信号驱动 `Presenter → View.render(snapshot)`。输入适配可直接调用应用服务；为简单按钮额外套一层转发类并非必需。Godot节点脚本可以承担模型或适配角色，判断边界看依赖和职责，不以是否继承Node机械划分。

选择理由：现有模型、Resource、交易和保存分区已经提供分层基础；界面需要集中格式化和输入转换，MVP能减少控件脚本承担业务；物理与动画继续使用原生场景组件。MVC可作为局部交互思路，项目不采用一个包揽日结、库存、地图和剧情的总Controller。当前实体规模不要求引入ECS或新的全局事件总线。

Godot官方的[场景组织建议](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html)支持独立场景通过依赖注入连接，由上层协调跨场景关系。本项目在此基础上选择MVP和应用服务，是结合当前代码的工程决策。

### 3.2 后续开发的落地契约

1. 新操作先明确输入、结果、唯一状态归属与失败行为，再选现有模型/服务扩展。库存、金币、日期只保留既有一份。
2. View只接收显示快照及用户意图，不自行扣物品、推进日期、扣费或写档。Presenter负责格式化和调用服务，不重新实现容量、价格、生产条件。
3. 需要黑屏、动画或物理的异步流程放引擎适配；关键结算放应用服务。并发按钮、重复信号和观察者重入不能重复收费、发奖或换天。保存失败需对用户可见并恢复输入。
4. 制作/设备使用独立实例状态和应用服务；动物新增实例身份、照料和产出事实，保留行为状态机；任务使用定义/进度/奖励用例；地图继续分离区域资源状态与场景适配。这些契约不等于相应玩法已经实现。
5. 动态物体必须先定义稳定实例ID、创建配置、快照编码/恢复与删除规则，再开放购买或摆放。恢复不走产出入口；不为新界面复制核心模型。
6. 旧模块渐进迁移。FarmTiller保持兼容外观，通过公开 `begin_tool_action/commit_tool_action` 接收工具命中；旧内部回调仅供过渡。新增肥料、品质、工具能力时建立专门规则/状态组件，不继续扩充旧脚本的动作分支。
7. 结构验收必须验证替换/移除具体View、重复提交、模型通知完整性及实际保存恢复；同时运行相关玩法与PCK检查。目录名字和类数量不是验收依据。

### 3.3 SOLID原则对照

| 原则 | 本项目的落实方式 | 后续禁止的回退 |
| --- | --- | --- |
| S：单一职责 | 时钟只管理日期；交易服务负责交易；界面只展示；文件存储与快照分离 | 在钱包里播放音效，在界面里实现扣费，在保存函数里发奖励 |
| O：对扩展开放 | 注册动物状态、购买策略、快照参与者和模态面板 | 每增加一种动物或面板，就修改多个核心脚本中的名称列表 |
| L：可替换 | 存储端口统一读写结果；状态统一 enter/tick/exit；失败保留已有事实 | 子类偷偷改变返回值含义、失败时部分扣费、恢复时重复掉落 |
| I：接口隔离 | 使用小型 Callable 端口、状态接口、编码/恢复接口 | 要求一个模块实现不相关的巨大管理器接口 |
| D：依赖倒置 | 在组合根注入用例步骤、交易规则、存储实现和表现回调 | 领域规则反向查找 UI 或自行创建外部服务 |

不为每个简单方法创建接口，也不因文件行数机械拆类。拆分应对应独立状态、规则、生命周期或外部边界，且有可验证的调用契约。

## 4 扩展入口

### 4.1 动物

- `AnimalProfile` 是共享且运行时只读的物种配置；每只动物持有独立 `AnimalStateMachine`。
- 普通新物种复用 `FarmAnimal`，提供 Resource、场景、碰撞体和动画；特殊图集只覆写表现适配。
- 新行为继承 `scripts/animals/states/animal_state.gd`，通过 `brain.register_state(id, state)` 注册，再用 `transition_to` 切换。不得让状态长期持有状态机或宿主引用，避免引用环。
- `enter`、`tick`、`exit` 各司其职；未知状态切换必须失败且保留原状态，同状态不能反复执行入场。
- 动物产物按每日事实结算，不在进入待机、觅食或睡眠时发放。
- 上线购买、成长和照料前，必须补齐个体 ID、归属、成长/照料与已结算日期的持久化。当前迁移不等于已经实现这些经营功能；随机目标等瞬时状态可以不保存。

### 4.2 每日结算

固定顺序为：结束当日生产 → 推进日期 → 更新次日天气 → 应用次日浇水状态 → 发布新日事件。

- 通过 `DailyCycle.on_finish_day` 与 `on_begin_day` 注册步骤，组合根负责明确先后顺序。
- 晴天未浇水不能因为次日下雨补长；雨天结束后的晴天必须清除新日的湿土标记。
- `TimeSystem.sleep()` 是兼容用例入口，不能重新把农田逻辑绑定到 `time_changed` 或依赖信号连接先后。
- 新增每日产出或奖励要记录已结算日期，保证重复事件、读档与过场跳过不重复发放。
- 工具命中必须同帧提交资源状态和收益，容量预检先于扣体力；掉落、计数或持久状态不能依赖倒树/消失动画的结束回调。满包时保留目标，动画中保存恢复不得丢失或重复收益。
- 作物换季和生长预算集中在 `crop_season_rules.gd`，商店由Presenter整理只读信息。恢复先读日期，再恢复植株并校验季节；枯萎不可自动复活，清理不发收获奖励。温室上线需显式接入受保护区域规则，不能把规则扩展参数当成已实现温室玩法。

### 4.3 交易与库存

- 交易调用 `TradeService.purchase/sell`，价格来自物品定义；UI 传入的旧价格参数只保留兼容签名。
- 购买资格通过 `add_purchase_rule` 扩展，失败返回原因，不在每种 UI 中重复校验。
- 整笔交易先确定数量、金币和容量；批量库存变更结束后再通知观察者，成功事件只发一次。
- `Inventory.add_item` 的来源必须明确：采集/收获用默认 `collection`，购买用 `purchase`，箱子转移用 `transfer`。购买和取箱不增加今日收获。
- 新增制作、交付等多资源事务时，复用同样的预检查和完整提交约定；不能先发成功事件再回滚。

### 4.4 模态界面

- 新面板继承 `ModalPanel`，使用 `_set_modal_open`，通过 `ModalCoordinator.register_panel` 注册。
- 暂停世界的面板设置 `pauses_world`；协调器统一管理互斥、世界暂停、输入锁与焦点恢复。
- 面板关闭或销毁必须释放自己的所有权；不能修改其他来源的过场/睡觉输入锁。
- 玩家和快捷栏不维护面板名称表。不要在新面板里直接改 `SceneTree.paused` 或调用玩家布尔输入锁。

### 4.5 持久化与世界对象

- 使用 `SnapshotRegistry.register_section(key, encode, decode)` 添加独立分区。恢复顺序须反映依赖：先基础模型和世界，再恢复依赖它们的任务与表现；最后发恢复完成通知。
- 当前正式格式为 v2。v1 通过 `SaveMigrations` 显式迁移；未来版本需增加迁移，不能覆盖或假装读取高版本存档。
- 存储实现遵守 `SaveStore` 端口：完整写入临时文件并 flush 后替换，保留上一份可恢复备份；失败返回 false，原正式档仍可读。
- 树石通过 `world_objects` 保存；旧的 `farm.rocks` 仅用于 v1 兼容入口，正式 v2 不保存第二份石头状态。
- 场景实例使用显式 `persistent_id`。当前历史 ID 中的数字坐标只是字符串的一部分；改位置、名字、遍历顺序时不能重算 ID。地图生成器表的第三列保留同一身份。
- 世界恢复使用初始模板加保存状态，不调用砍树、采矿、交付等会产生收益的入口。连续恢复三次，库存和奖励不能增长。当前模板集合覆盖场景中的静态树石；新增可放置设备和购买动物时，还须提供动态实例的创建配置与重建工厂，不能只写一个状态分区。
- 外部 JSON 的结构和标量需验证；新参与者负责自己内层结构的校验。不能只判断顶层是 Dictionary 就宣称坏档安全。

### 4.6 导航与场景生命周期

- 导航扫描真实且启用的嵌套静态碰撞体；不能假定 `StaticBody2D` 位于 `World` 第一层。
- 碰撞变化发 `obstacle_changed`，由组合根接导航刷新；树石不查找导航服务。
- 刷新请求同帧合并，重建必须清空上一版阻塞标记。测试同时覆盖障碍加入和移除。
- 退出场景清理注册回调与持久化模板；不得留下引用旧会话的回调或重复信号连接。
- RefCounted的Presenter/服务必须由组合根或所属实例显式持有；不能只留下指向它的Callable。Presenter离树时解除自己建立的全部绑定，包括View直接连到服务的信号。
- 新增异步过场使用单一重入保护和操作有效性校验，销毁时释放自己的输入锁与黑幕；必须覆盖淡出中和等待计时中的退出。
- 延迟回调不能强持有可能提前释放的世界节点；使用弱引用，并检查目标仍有效且在树中。
- 应用退出统一调用 `scripts/platform/app_lifecycle.gd`，在引擎结束前停止音频、取消 Tween、释放音频流，并等待音频线程回收。关闭标题界面不能写入空快照覆盖玩家进度。
- 从资源目录发现配置时使用 `ResourceLoader.list_directory`；不能假定导出包中存在原始 `.tres` 文件。向实例场景内部添加节点时保留对应 `[editable path="..."]`，并用 PCK 运行检查确认角色和交互节点没有在二进制场景转换时丢失。

## 5 验证规则与命令

在项目根目录运行：

```powershell
pwsh -NoProfile -File tools/run_checks.ps1
pwsh -NoProfile -File tools/run_checks.ps1 -Suites check_architecture,check_basic_loop
pwsh -NoProfile -File tools/run_checks.ps1 -Suites check_basic_loop -Packaged
```

可通过 `-GodotPath` 指定引擎，`-TimeoutSeconds` 指定单套检查上限，`-Windowed` 验证真实窗口渲染。入口复制源码/素材建立固定快照，校验复制前后文件指纹，完成资源导入，每套检查使用不同的 `PixelFarmChecks_*` 用户目录。日志、源码清单和 `results.json` 保留在打印的临时目录中。全量运行包含 PCK 导出与包内经营/保存检查；指定套件时可追加 `-Packaged`。PCK 运行通过不等于 Windows 独立 EXE、安装或发行渠道已验收。

- 检查脚本必须调用 `tools/lib/check_safety.gd` 的 `require_isolated`。正式项目直接运行回归应拒绝，不能删除或改写真实玩家槽位。
- 并行编辑期间复制快照发生变化时，入口最多三轮同步差异文件，核对源码与快照完整指纹一致后才运行。删除文件或持续变更时仍失败，不能通过忽略指纹检查运行混合版本。
- 检查正常退出码、关键断言、末尾执行标记；`SCRIPT ERROR`、解析错误和非预期引擎错误一律失败。
- 退出资源泄漏也算失败，不再豁免 Dummy 音频告警。检查通过 `tools/lib/check_lifecycle.gd` 清理并输出末尾标记；包外入口使用相同的应用生命周期边界。实际窗口运行与自动逻辑验证分开说明。
- 覆盖成功与失败路径：金币不足、满包、无效数量、跨日天气、旧档迁移、写入失败、重复加载、面板交接与销毁。
- 扩展机制要有替身验证：注册一个新动物状态、新保存分区或新购买规则，无需修改核心服务也能工作。
- 新功能的最小路径验证后，再运行其依赖的集成检查；新失败或新增代码才需要重复相应检查，不能只跑静态资源存在检查。
